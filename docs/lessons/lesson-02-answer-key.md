# 第 2 课 · 验收问答标准答案

> 用途：复习资料。先自己答，再对照。

## Q1．QoS 报文序列

- **QoS 0（至多一次）**：发送方发一个 `PUBLISH`，结束。不确认、不重发、不存储，丢了就丢了。
- **QoS 1（至少一次）**：`PUBLISH`（带 Packet ID）→ 接收方回 `PUBACK`。发送方超时没等到 PUBACK 就重发，重发报文带 **DUP 标记** → 所以可能重复，接收方业务要幂等。
- **QoS 2（恰好一次）**：`PUBLISH → PUBREC → PUBREL → PUBCOMP` 四次握手，双方为每条消息维护两阶段状态。

**容易漏的点**：QoS 是**逐跳**语义——"发布端→Broker"和"Broker→订阅端"是两段独立的 QoS 流程（实验 5 里 Dashboard 的 PUBREC/PUBREL/PUBCOMP 各涨两轮就是证据）。

## Q2．就低原则

- 发布 `-q 2` + 订阅 `-q 1` → 收到 **QoS 1**
- 发布 `-q 1` + 订阅 `-q 2` → 还是 **QoS 1**
- 规则一句话：**有效 QoS = min(发布 QoS, 订阅时授予的 QoS)**。实验 4 的 `0, 1, 1` 就是这么来的。

## Q3．互踢事故

- **为什么断**：MQTT 规范要求，Broker 收到相同 Client ID 的新 CONNECT 时，**必须断开旧连接**（新的顶掉旧的）。
- **双方都自动重连**：A 上线踢掉 B → B 重连踢掉 A → 无限循环。监控上表现为设备高频上下线（flapping），日志刷屏，极难一眼看出根因。
- **企业策略**：Client ID 全局唯一规范（如 `{productKey}.{deviceName}`）；App 端同一账号多设备登录时附加安装实例指纹/随机后缀。反向用法：设备端故意用**固定 ID**，让重启后的新连接主动顶掉 Broker 上的僵尸连接——两种策略按场景选。

## Q4．通配符（含陷阱题）

向 `wbiot`（无子层级）发布：

- `wbiot/+` **收不到**——`+` 必须恰好匹配**一层**，`wbiot` 后面没有任何层
- `wbiot/#` **能收到**——`#` 匹配"任意多层，**含 0 层**"，即父层级本身

用 `mqttx pub -t 'wbiot/+'` 发布（实测 mqttx CLI v1.13.0）：

```
✖ You cannot publish the message to a Topic that contains wildcards characters #, +
（exit code 1，客户端直接拦截，请求根本没发往 Broker）
```

**两层防线**：规范的客户端库在本地就校验拦截；如果某个库不校验，报文到达 Broker 后会被视为**协议违规**，EMQX 会直接断开该连接。结论不变：通配符只属于订阅。

## Q5．心跳保活

- 无业务消息时，客户端按 Keep Alive 周期发 `PINGREQ`，Broker 回 `PINGRESP`——连接就靠这个"活着"（实验 2 的 `_checkPing` 日志）。
- Broker 判死标准：**1.5 × Keep Alive** 时间内没收到该客户端的**任何**报文（业务报文也算数），即判定离线并断开，随后触发遗嘱（第 7 课）。

## Q6．为什么"QoS 1 + 业务幂等"普遍优于 QoS 2

1. **报文数量**：QoS 1 每条消息 2 个报文，QoS 2 要 4 个；且逐跳生效，端到端翻倍——吞吐与延迟差距立现。
2. **Broker 状态维护**：QoS 2 要求收发双方为每条在途消息维护两阶段会话状态。单条无所谓，百万级连接下内存和存储成本是量级差异。
3. **极端情况兜底**：QoS 2 的"恰好一次"只覆盖 MQTT 传输这一段。消息落库、跨系统转发、业务层重试等环节照样可能产生重复——所以**业务幂等无论如何都躲不掉**。既然幂等必须做，QoS 1 + 幂等就用一半的成本覆盖了 QoS 2 的实际价值，QoS 2 沦为"贵且不彻底"。
